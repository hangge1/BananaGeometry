# 开发与质量规则

## 项目内 skill 原则

仅使用本项目中的 skill，不使用其他目录、用户级安装或插件提供的外部 skill。确需补充时，优先搜索网上已有方案，审阅适用性、许可证及脚本行为，经过项目化整理后再使用。当前项目没有必须使用的 skill，不为普通编码额外引入 skill。

此原则优先于此前聊天中提到的外部技能工作流。项目原有 `AGENTS.md` 保留，本文件记录后续新增要求。

## 开发日志

每个实际完成的阶段在 [开发日志](development-log.md) 中记录目标、变化、实现决定、验证结果和剩余问题。用户新增约束应及时落盘，不依赖聊天记忆。

## Git 版本管理

使用本地 Git 仓库。代码、依赖版本与哈希、用例及文档进入版本管理；第三方源码、构建产物、下载缓存、机器配置不进入版本管理。发布目录携带第三方许可证。不创建远程仓库或推送，除非用户另行要求。

阶段版本应对应可描述、可验证的变化。提交前检查差异和意外文件；提交信息采用简短的 `docs:`、`chore:`、`feat:`、`fix:`、`test:` 前缀。发现失败检查时先修复或明确记录，不把失败描述为通过。

### 小步提交原则

- 一次迭代只完成一个明确的小目标，采用“实现 → 相应测试 → 审查差异 → 本地提交 → 更新日志”的循环。
- 不等整个功能完成后再集中提交，不用一次大提交代替多次可验证迭代。
- 每个提交应独立可构建、可验证；构建配置需随该步能力同步演进，不能引用尚未进入版本的文件。
- 构建、核心数据、Lua SDK、示例用例、原生界面、交付文档分别组织，必要时继续细分。
- 如果 Git 提交因环境权限受阻，暂停扩充功能，先解决提交阻碍；不要继续积累大量未提交代码。
- 对既有实现整理版本时，应明确这是对现有工作的补录，并使用各提交的独立文件树验证。不能仅按文件分批暂存、留下无法构建的中间提交，也不伪装为此前已有的开发记录。

## 自动化测试

当前代码与注释规范见 [代码规范](coding-style.md)，以 Google C++ 和适用于本项目的 Neovim Lua 约定为基准。该规范替代早期四空格与不引入测试框架的默认约定。

模块化是强制开发原则：目录、文件和构建目标按职责划分，依赖方向明确，不把互不相关的实现集中到单个文件。先建立回归测试，再逐步拆分现有混合职责，避免只移动文件而不消除耦合。

通过 CTest 统一运行 Catch2 单元测试，性能测量采用独立 Google Benchmark 目标；Lua 测试使用同一嵌入式引擎，覆盖实际 SDK 和示例行为。新增框架仅用于开发验证，不增加应用运行时依赖。

重点覆盖坐标转换、命中、编辑事务、撤销重做、保存加载、实例隔离、异常与重载回滚。窗口集成和性能验证单独记录；自动化无法证明的视觉及手工行为须明确列出。

每个阶段完成前运行相应检查。测试需要断言行为，不能只检查文件存在或简单复制实现。
