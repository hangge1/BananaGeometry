- **D21：只使用项目内 skill**。如需补充优先搜索公开方案并审阅后项目化，不使用其他目录的 skill。
- **D22：开发日志、Git 与自动化测试**。开发过程持续留痕，使用本地 Git 管理版本，通过 CTest 运行行为测试。

- **D24：小步提交、增量迭代**。每次围绕小目标实现、测试和提交，提交必须能独立构建；Git 受阻时暂停新增功能，不继续囤积变更。

## 2. 曾比较的路线

### 第一轮：以扩展、性能和使用便利性为主

| 路线 | 优势 | 主要代价 |
| --- | --- | --- |
| Python + PySide6，必要时 NumPy / 原生扩展 | 临时用例开发方便，Qt 二维交互能力成熟 | 解释器、Qt 和额外包的分发成本；密集 Python 回调可能成为瓶颈 |
| C# + .NET + Avalonia | 类型与工程支持完善，适合复杂插件长期维护 | .NET 运行时与 UI 框架；对象编辑能力仍需自建 |
| TypeScript + Web + Konva，必要时 Worker / Wasm | UI 组合与分享方便，二维库能力丰富 | 工具链与库依赖，本地文件及原生算法接入差异 |

这些是当时的候选，不是当前需要同时实现或保留的技术栈。新增轻量化要求后，选型权重发生变化。

### 第二轮：依赖与工程精简优先

| 路线 | 讨论结论 |
| --- | --- |
| C++ + Dear ImGui + 系统接口 | 原生计算、依赖可控，适合演示和调试工具；选为宿主路线 |
| 原生 JavaScript / TypeScript + Canvas + HTML 控件 | 第三方运行库可很少，但仍依赖浏览器，本地插件与文件交互需适配 |
| C# + WinForms | 可不依赖第三方 UI 框架，但仍需要管理 .NET 运行时 |

确认仅 Windows 后，窗口和图形层使用 Win32 / Direct3D 11，首版无需 SDL3 等跨平台窗口库。若未来要求跨平台，应单独评估这一决策的影响。

### 第三轮：用例无需编译

| 脚本选择 | 讨论结论 |
| --- | --- |
| Lua | 轻量、嵌入接口简单；需要 SDK 提供公共绘图与交互能力，用户选择采用 |
| JavaScript + QuickJS | 也是小型嵌入方案，但不自带浏览器和 Node.js 的宿主功能 |
| Python | 算法生态便利，但解释器、标准库和包管理负担较大 |

采用标准 Lua 作为首版脚本引擎，不默认增加 LuaJIT、多语言运行时或脚本绑定框架。

## 3. 已排除的误解

- “完整 SDK”不等于必须引入大型图形编辑框架。
- “轻量”不等于不给用例提供公共交互能力，让每个用例重写选择与拖拽。
- “无需重新编译”不等于保存脚本后必须自动热更新；当前方案是手动重载并重置。
- “保存”是保存可继续编辑的用例数据，不是只导出图片。
- “撤销”针对数据编辑，不记录所有鼠标键盘事件。
- “无限视图”是二维世界坐标浏览方式，不代表无限数值精度或无限数据容量。
- 脚本计算、命中检测和渲染是不同的性能来源。已有千级对象创建与数据提取测量，结果不等同于 GPU 帧率或全场景性能保证。
